To supply your own help command, call `cmd.SetHelpCommand(cmd *Command)` on the root/parent command, passing a `*Command` you've built yourself. This is documented in site/content/user_guide.md under the "Defining your own help" section (evidence ref e4/e64, line 541, span 535-547): "You can provide your own Help command or your own template for the default command to use with the following functions: ```go cmd.SetHelpCommand(cmd *Command)". The same section notes that if you use the generated `help` command instead, you can still customize its position in help output via `SetHelpCommandGroupId()` on the root command.

If you don't want a full replacement command but just custom help text/behavior, override the help function instead: `cobra.Command.Help()` (command.go:473, evidence e2/e62) is documented "Can be defined by user by overriding HelpFunc" and its body is just `c.HelpFunc()(c, []string{})` — i.e. Help() delegates to whatever `HelpFunc` is set on the command, so setting that field (e.g. via a `SetHelpFunc` accessor) is the lighter-weight customization path.

One implementation detail to be aware of: `cobra.Command.InitDefaultHelpCmd()` (command.go:1229, evidence e3/e63) auto-installs the default help command "automatically by executing the c or by calling help and usage," but explicitly does nothing "If c already has help command or c has no subcommands" (it checks `if c.helpCommand == nil` before creating one). So calling `SetHelpCommand` with your own command before `Execute()` will prevent the default help command from overwriting it.

Also relevant but not detailed in this response: `HasHelpSubCommands()` (command.go:1603, evidence e1/e61) determines whether a command has any available additional-help-topic subcommands to list, which affects how custom/additional help entries show up in the default usage template.
