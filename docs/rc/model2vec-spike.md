> **Story:** SW-259 · **Spec:** semantic-search-wow-and-token-savings · **Status:** decided
> · **Date:** 2026-08-30 · **Package:** `internal/spike/model2vec` (throwaway; imported by nothing;
> SW-262 supersedes or deletes it) · **Pins:** `internal/spike/model2vec/PINNED.md`

The largest technical risk of the static-embedder track is not model quality but **format and
tokenizer fidelity**: can graphi reproduce `tokenizer.json`, float16 safetensors, mean pooling
and L2 normalisation exactly as the Python `model2vec` reference does — in pure Go, CGo-free,
with zero egress? This record answers that from measurements, not from a claim. Every number
below is produced by a test under `internal/spike/model2vec`; the commands that reproduce it are
named beside it.

No epsilon loosening was needed. Exactness came from mirroring numpy's float16 arithmetic
(mean stored as float16; squares, pairwise sum of squares, sqrt and division each rounded to
float16) rather than from a looser tolerance — the clean float32 pipeline would have failed AC-3
by 24×, which is the concrete argument for SW-262 to fix the pipeline's rounding points as part
of the determinism contract (spec decision 4), not just the summation order.

### 2.1 Finding: the reference is not batch-invariant — and a requirement for SW-262

`tokenizer.json` declares `padding: BatchLongest, pad_id 0`. `Tokenizer.encode_batch_fast`
applies it and model2vec strips only the unk id afterwards, so in a batch every text shorter
than the longest one pools `(longest − own)` copies of the `[PAD]` embedding row into its mean.
The oracle's own batch block shows it: of the 8 texts only the longest (15 tokens) equals its
single-text vector.

**The spike therefore ships both, and AC-3 is measured against the reference-faithful one:**

- `Embed(texts)` **is the reference**: it applies `BatchLongest` padding with the pad id read from
  `tokenizer.json` (never hardcoded), so replaying the oracle's batch through the public API gives
  max \|Δ\| = 0. This is what §2's table and the AC-3 criterion cite.
- `EmbedEach(texts)` is `encode([t])` per text — **batch-invariant** by construction:
  `EmbedEach(batch)[i]` is bit-identical to `Embed([]string{t_i})[0]` for every `i`
  (`TestEmbedEach_BatchInvariant`), and its divergence from `Embed(batch)` is exactly the padding
  effect, 2.14e-4 on the pinned batch (`TestEmbedEach_DivergenceFromEmbedIsPadding`).

**Requirement carried to SW-262, not a doubt:** the production embedder must adopt **`EmbedEach`
semantics** — a node's vector must not depend on which other nodes share its embedding chunk, or
the index fingerprint stops describing the vectors. SW-262 pins that choice in `Embedder.ID()` /
the model pin and states it in the docs, because a user comparing graphi's vectors against
`model2vec.encode(list)` will otherwise see a legitimate-looking mismatch. The reference-faithful
`Embed` stays available as the oracle-comparison path.

### 2.2 Documented limits (not covered by the oracle; PINNED.md)

Canonical reordering inside NFD is not performed (every nonspacing mark is stripped right
after); the Rust `unicode_categories` tables tokenizers use are older than Go 1.26's, so a very
recently assigned code point is dropped by the reference and kept here; the added-token
`single_word` boundary predicate is implemented from the spec, not from a fixture. A fixture
regeneration adding `"[UNK]"`, `"a [PAD] b"`, `"x[PAD]y"`, a U+0130 and a recent emoji would
close these — none of them touches identifier or English-prose text.

Single-threaded, no SIMD, no allocation tuning. The 32 MiB table is held as binary16 (the
artifact's size) and decoded per lookup; the ~40 MiB above the table is the tokenizer's 63k-entry
vocabulary map and Go's heap headroom.

**No causal claim is made about the gap between the two rows.** An earlier draft explained the
production path as "slower than the old per-text figure" because it pays one `Tokenizer.Encode`
per text — that explanation was wrong twice over: at `00c8928` the public `Embed` *was* the
per-text loop, so the "old" 55,140 texts/s figure is itself an `EmbedEach` figure and the
comparison was the same code against itself; and the production path is consistently the *faster*
of the two, not the slower. The spread across runs (23k–54k texts/s for `EmbedEach`) is
run-to-run variance on this runner, not a semantic cost — a review re-run on this same tree
measured `EmbedEach` at 53,862 texts/s (warm 54,416) against the reference path's 27,621. Read the
two rows as "both are fast enough by a wide margin", and note only the measured fact that the
reference path pools ~2.9× more tokens (490,000 / 169,987) — whether that is what costs it the
difference is not established here. Anything finer needs a quiet machine and more runs than a
spike warrants. For
scale: cobra (938 nodes) embeds through `EmbedEach` in roughly 20–40 ms here, a 50k-node
repository in about one to two seconds.

All four conjunction members hold, from measurements taken through the public API. Three things go
to SW-262 as **requirements, not doubts**: adopt `EmbedEach` (batch-invariant) semantics and pin
that choice in `Embedder.ID()` (§2.1); carry the float16 rounding points and the fixed summation
tree into the determinism contract (§2); and validate the tokenizer's `padding` section fail-closed
so chunk composition can never silently change a vector. SW-262 may proceed; Ollama/ONNX remain the
opt-in backends they are today until it lands.

Review history: round 1 (codex, read-only) returned `changes-needed` on exactly this point — the
public `Embed` was batch-invariant while the oracle batch used `BatchLongest` padding, so AC-3 was
not met *by the public API* even though the arithmetic was understood. The rework made `Embed` the
reference and moved batch-invariance into `EmbedEach`; the criterion above is now measured through
the API a caller actually uses. Round 2 (same reviewer) returned `changes-needed` again because
the AC-4 / AC-5 tests still called the now-padded `Embed`, so the recorded §3/§4 numbers belonged
to the behaviour now named `EmbedEach`, while the tests exercised the padded path. This rework
switches both tests to `EmbedEach`, splits the throughput table so the headline figures name the
production path (with the tokens that path pools) and the reference path is reported separately
(labeled, with its pad rows counted), and re-evaluates the §7 prose against the measured numbers.
